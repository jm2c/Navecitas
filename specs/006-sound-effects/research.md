# Research: Sound Effects for Game Events (Phase 0)

**Feature**: `006-sound-effects` | Resolves every open question in plan.md §Technical Context; all decisions respect the constitution (v1.0.0, amended to v1.1.0 for this feature's explicit sound scope) and the clarification session (2026-10-24). The spec left **no** NEEDS CLARIFICATION; this phase resolves the audio architecture, event capture, cue design, browser lifecycle, test strategy and scope boundaries.

---

## R1 — Audio production approach: synthesized cues, no audio files

**Decision**: Produce every sound effect locally with the browser's Web Audio API using oscillators, gain envelopes, filters and one generated noise buffer. Ship **zero** audio files. Use a small pure-data cue catalog (`src/audio/cues.js`) consumed by a browser-only engine (`src/audio/engine.js`).

**Rationale**:
- The user explicitly chose **synthesized retro/arcade effects generated by the game** (clarification 2026-10-24), so recorded assets are out of scope.
- Zero audio files means zero audio provenance/licensing work, zero download/decode latency and no network dependency; this directly satisfies FR-015, FR-022, FR-016 (vacuously) and SC-011.
- Synthesis gives precise control over pitch contour, timbre and duration, which is the cheapest way to guarantee that the eight requested event types are mutually distinguishable (FR-010, SC-002).
- The Web Audio API is a platform API, not a dependency; it satisfies constitution I and is already available in every target desktop browser.

**Alternatives considered**:
- **Bundled free-to-use recordings (CC0/CC-BY)** — viable but introduces file downloads, decode timing, asset provenance, license text and a larger repository; rejected by the clarification.
- **External audio CDN** — rejected: violates offline play (FR-015) and the zero-external-service constraint.
- **Pre-rendered WAV data URIs inside JavaScript** — self-contained but bloats source, requires a generation step, and provides no benefit over real-time synthesis for short cues.
- **HTMLAudioElement pools** — rejected: higher latency, autoplay restrictions are harder to manage, and seamless overlapping is less reliable than scheduled Web Audio nodes.

## R2 — Event capture: a pure semantic event queue in the core

**Decision**: Add a DOM-free `src/events.js` exporting frozen event ids plus `emitEvent(state, id)`, `drainEvents(state)` and `clearEvents(state)`. Extend `createGame()` with a transient `events: []` array. Core modules push semantic events at the exact mutation points:

| Event id | Emitted from | Condition |
|---|---|---|
| `countdown:3` | `src/update.js` `phaseMachine` | `START → COUNTDOWN` sets step `3` |
| `countdown:2` | `src/update.js` `phaseMachine` | step advances `3 → 2` |
| `countdown:1` | `src/update.js` `phaseMachine` | step advances `2 → 1` |
| `countdown:go` | `src/update.js` `phaseMachine` | step advances `1 → GO` |
| `shot` | `src/update.js` `fire` | after a successful trigger pull (one event even for double shot) |
| `asteroid:destroyed` | `src/score.js` `applySizeRule` | a `SMALL` asteroid is removed |
| `asteroid:split` | `src/score.js` `applySizeRule` | a `MEDIUM`/`LARGE` asteroid creates two fragments |
| `life:lost` | `src/collision.js` `hitShip` | a non-shielded ship hit removes a life (also on the final hit) |
| `life:gained` | `src/score.js` `grantLife` | a life pickup is obtained by ship contact or projectile, including at max lives |
| `powerup:collected` | `src/collision.js` | a `POWERUP` is obtained by ship contact or projectile |
| `game:over` | `src/collision.js` `hitShip` | the final life is lost and the phase becomes `GAME_OVER` |

The browser layer drains the queue once per rendered frame (`drainEvents(state)`) and hands the ids to the audio engine; the core never imports browser APIs.

**Rationale**:
- Semantic events are more precise than observing state differences. A state-diff listener cannot reliably detect a life pickup collected at `MAX_LIVES` (no state change), cannot tell a double-shot trigger (two projectiles) from two triggers, and makes split-vs-destroy and same-tick chain reactions ambiguous.
- The event ids are strings in a frozen object; the core stays DOM-free and testable with `node --test`. Existing `update`/`collision` signatures do not change.
- `events` is transient output, never read by gameplay rules, never serialized, and cleared by the audio consumer or on visibility hidden. The existing gameplay tests do not assert the exact shape of `GameState`, so no expectation changes are needed.
- The queue preserves occurrence order, which is enough for mixing; the audio layer does not need gameplay internals.

**Alternatives considered**:
- **State diffing in an audio director** — rejected: misses max-life pickups, double-shot distinction and some same-frame events; fragile coupling to entity shapes.
- **Passing callbacks/event sinks into `update` and `collision`** — rejected: changes the signature of every core entry point and test, for no functional gain.
- **A module-level global event bus** — rejected: leaks state between tests and game instances; a per-state queue is simpler to reason about.
- **Returning events from `update`** — rejected: forces the fixed-step loop to understand audio and changes the established `update(state, dt, input, random)` contract.
- **Reading input/frame data in the audio layer** — rejected: duplicates core logic and would drift from the real firing/collision rules.

## R3 — Cue catalog, distinctness and mix

**Decision**: Model cues as pure data with a `durationMs` and a list of tone/noise layers. Proposed catalog (values are audio-only and may be tuned during quickstart V2, within the constraints below):

| Event | Character | Layers (summary) | Duration |
|---|---|---|---|
| `countdown:3` | short rising-family beep | square 440 Hz | 90 ms |
| `countdown:2` | same family, higher | square 523.25 Hz | 90 ms |
| `countdown:1` | same family, higher | square 659.25 Hz | 90 ms |
| `countdown:go` | bright two-tone start signal | triangle 880 Hz + square 1174.66 Hz delayed | 320 ms |
| `shot` | quick downward laser | square 920→300 Hz + tiny high-pass noise click | 90 ms |
| `asteroid:destroyed` | dull impact/boom | low-pass noise 1200→180 Hz + sine 110→50 Hz | 220 ms |
| `asteroid:split` | sharp crack + two fragments | high-pass noise 2200→900 Hz + two short square blips (700/950 Hz) | 130 ms |
| `life:lost` | long descending negative tone | sawtooth 440→110 Hz + triangle 220→55 Hz | 520 ms |
| `life:gained` | ascending positive triad | triangle 523.25 / 659.25 / 783.99 Hz, staggered | 340 ms |
| `powerup:collected` | fast rising reward zap | square 600→1400 Hz + triangle 1200→1800 Hz | 200 ms |
| `game:over` | slow descending final triad | triangle 392 / 329.63 / 261.63 / 196 Hz, stepped | 1000 ms |

Constraints:
- Every event id maps to exactly one recipe; no event shares a recipe. Rapid-fire shots reuse the same recipe, as expected.
- All recipes are non-looping and ≤ 1.5 s (FR-012); the longest is the game-over cue at 1.0 s.
- Each cue uses a different contour/timbre family from the others: countdown = short beeps (GO longer/two-tone); shot = fast downward tonal; destruction = low noise/thump; split = bright crack + double blip; life lost = long falling; life gained = rising triad; power-up = fast rising zap; game over = slow falling triad. This is the design basis for FR-010/SC-002.
- Mix chain: one `GainNode` (master) → one `DynamicsCompressorNode` (threshold ≈ −18 dB, ratio ≈ 12, short attack) → destination. Per-layer gains stay in a narrow 0.02–0.10 range; short attack/release ramps (3–10 ms) avoid clicks. The compressor prevents clipping when rapid-fire, splits and pickups overlap (FR-012, SC-004).
- One generated white-noise buffer (≈1 s) is created once after the context unlocks and reused with random offsets; no per-cue buffer allocation.

**Rationale**: The chosen combination makes each cue identifiable by contour (up/down/steady), timbre (tonal vs noise) and length rather than by volume alone, which is what SC-002 tests. A narrow gain range plus a compressor keeps the mix safe without a per-cue loudness normalization step.

**Alternatives considered**:
- **One shared recipe with pitch changes for all events** — rejected: too easy to confuse, especially destruction vs split and life lost vs game over.
- **A separate pre-rendered asset per cue** — rejected by R1.
- **Per-cue gain normalization to a fixed loudness** — overkill for short arcade cues; manual balance is simpler and the compressor catches peaks.
- **Stereo panning/positional audio** — rejected: no gameplay value, and the spec does not request it.

## R4 — Browser audio lifecycle: unlock, resume, hide and failure

**Decision**:
- Create the `AudioContext` **lazily on the first deliberate input** (`keydown` or `pointerdown`). The engine attaches idempotent unlock listeners; the game already starts on Space, so the first countdown cue is covered. No AudioContext is created at page load.
- On unlock: create the context (with the `webkitAudioContext` fallback), build the master gain/compressor chain, resume if suspended, and flush any still-fresh pending events.
- `playEvents(ids)` is called once per rendered frame before drawing. If the context is running, schedule immediately at `currentTime + ~5 ms`. If it is not running yet, keep the events in a small bounded pending list with timestamps; on resume, play only entries younger than ~300 ms so a long-blocked context cannot replay a stale burst. Cap the list at 32 entries.
- On `visibilitychange` hidden: stop every active source node (tracked in a small `Set`), `suspend()` the context, clear the pending list and let `main.js` clear `state.events`; on visible, `resume()` only if a context already exists. No queued cue and no partially played cue survives a hide/show cycle (FR-019, SC-010).
- All cues are finite, one-shot events. The required game-over cue plays once at the transition and finishes; no cue loops or remains queued. Residual projectile/asteroid collisions after game over are existing gameplay events allowed by US3 #5 and may still emit their own cue; they are not a hidden-tab backlog or a repeated game-over cue.
- If Web Audio is unsupported: never throw; mark the engine unavailable and skip cues. If context construction throws or resume rejects: never throw; stay silent and retry on a later deliberate gesture. If the context exists and a later gesture resumes it, cues resume automatically without restarting the game (FR-017, SC-007).
- Audio-engine state (`context`, `pending`, `hidden`, `unavailable`) lives only in `src/audio/engine.js`; it is never added to `GameState`.

**Rationale**: Deliberate-input unlock is the standard way to satisfy autoplay policies (FR-018). The timestamped pending list handles the few-millisecond gap between the start gesture and a running context without allowing an unbounded backlog. Silencing on hidden prevents notes continuing while the tab is in the background. Keeping the state out of the game state preserves the core's purity.

**Alternatives considered**:
- **Create the context at boot** — rejected: browsers may create it suspended and log autoplay warnings; it also risks the first cue being blocked.
- **No pending queue** — rejected: the first countdown cue could be lost if `resume()` has not settled when the render frame runs.
- **Unbounded queue** — rejected: a long-blocked context would produce a delayed burst, violating the no-backlog requirement.
- **One AudioContext per cue** — rejected: browsers limit contexts; expensive and unnecessary.
- **Permanently disable audio after one resume failure** — rejected: the spec requires automatic recovery when audio becomes available.

## R5 — Integration points, test-first strategy and regression locks

**Decision**:
- New DOM-free files: `src/events.js`, `src/audio/cues.js`. New browser-only file: `src/audio/engine.js`.
- Modified core files (event emission only): `src/state.js` (add `events: []`), `src/update.js` (countdown + shot), `src/score.js` (destroy/split + life gained), `src/collision.js` (life lost, power-up, game over).
- Modified boot: `src/main.js` creates the engine, drains events before each render, clears the event queue when the tab hides, and lets the engine own its unlock/visibility listeners. `src/loop.js`, `src/input.js`, `src/entities.js`, `src/spawn.js` and `src/config.js` are unchanged. `index.html`, `server.js`, `assets/` and the render layer are unchanged.
- Tests are written first (red-green), then the implementation:
  - `tests/audio-cues.test.js` (fails before `src/audio/cues.js`): every event id has exactly one recipe; no extras/missing; all durations ≤ 1500 ms; every recipe has at least one layer with a positive gain; all recipe signatures are unique; the GO recipe is distinct from the three digit recipes; no URL/path/audio-file fields exist in the catalog.
  - `tests/events.test.js` (fails before emission exists): countdown emits each step exactly once in order; a successful shot emits one `shot` (double shot still one); blocked shots emit none; a small asteroid emits `asteroid:destroyed`; a medium/large split emits one `asteroid:split` per parent; a non-final hit emits `life:lost` and no `game:over`; the final hit emits `life:lost` then `game:over` exactly once; a life pickup emits `life:gained` by projectile and by contact, including at `MAX_LIVES`; a power-up emits `powerup:collected` by projectile and by contact; `drainEvents` returns events in order and clears the queue.
- Existing 13 `node --test` suites must stay green without expectation changes. They cover the gameplay rules that must not move.
- Manual validation lives in `quickstart.md` (V1–V13), including listening tests, autoplay, hidden-tab, rapid-fire mixing, offline and no-audio-files checks.

**Rationale**: The core delta is event emission only, so DOM-free unit tests can prove the exact event counts and conditions. The browser-only engine cannot be meaningfully tested with `node --test` without a DOM/audio mock; the constitution forbids adding browser dependencies, and manual listening is the honest validation for timbre/distinctness. The test suite catches the realistic regressions (missing events, duplicate events, wrong trigger, cue catalog drift) while the quickstart covers the audible result.

**Alternatives considered**:
- **Mock AudioContext in Node** — rejected: a large mock for little value; it would test the mock, not the sound.
- **Add Playwright/Puppeteer** — rejected: violates the zero-dependency constitution and the project's manual visual/audio validation pattern.
- **No new tests** — rejected: event counts and cue coverage are exactly the kind of regression that would otherwise ship silently.
- **Modify `loop.js` to flush audio** — rejected: main's render wrapper already runs after all updates in a frame and keeps the loop generic.

## R6 — Performance, latency and overlap

**Decision**:
- Drain and schedule at most one frame's worth of events per render; normal event volume is tiny (shot cadence ≤ 6.25/s; splits/pickups occasional). The queue is read once per frame, then cleared.
- Create oscillators/gain nodes per cue and let them stop and be collected; no per-frame node creation when idle. The noise buffer is built once.
- Schedule at `currentTime + 5 ms`, well within the spec's 100 ms latency bound (SC-003).
- Do not add a voice cap in normal play; a dense same-frame chain (e.g., several splits plus a pickup) is a handful of short nodes. The master compressor is the safety net for peaks; if listening tests reveal clipping, lower per-layer gains before adding a voice manager.
- No new rAF loop, no timers, no per-frame `fetch`, no audio-file decode. Rendering remains the only per-frame work plus a small array iteration.

**Rationale**: Short scheduled Web Audio nodes are cheap and self-releasing. The existing game already caps projectiles and asteroid spawns, so cue volume is bounded. This preserves the 60 FPS target and avoids the complexity of a voice pool.

**Alternatives considered**:
- **Voice pooling/stealing** — deferred until measurements show a need; it adds complexity and can drop cues, conflicting with SC-004.
- **Pre-rendering cues with OfflineAudioContext** — possible optimization, but adds startup work and caching; unnecessary at this scale.
- **RequestAnimationFrame-driven audio scheduling** — rejected; scheduling at the event time via `currentTime` is more accurate.

## R7 — Scope firewall

**Decision**: Do **not** change any gameplay rule, constant, timing, radius, score, spawn rate, phase transition or visual. The only core changes are event emission and the transient `events` array. The audio feature explicitly excludes music, voice-over, ambient loops, in-game mute/volume controls, audio settings, persistence and any recorded audio assets. It adds no npm package, no build step, no server route and no `index.html` change. The render layer is untouched.

**Governance**: Constitution Principle V still lists "sound" among excluded features. Because spec 006 explicitly amends that scope (spec §Assumptions, FR-001), implementation must also update `.specify/memory/constitution.md` Principle V and bump the version to **1.1.0** with the amendment date, as the Governance section requires. This is a scope amendment, not a principle violation.

**Rationale**: Keeping the diff to semantic events plus a browser-only audio module makes the "no gameplay change" claim auditable, analogous to the 005 visual refresh's render-boundary firewall.

**Alternatives considered**: none — anything outside these boundaries would exceed the clarified scope.
